# Reference Map

This folder is the passive shared mechanics reference for TypeScript work in Node.js and Bun projects. It routes nine questions to the nine detail pages that carry this reference's answers: each route names the discriminating clue that selects its page, and the page carries the explanation. Its subject is TypeScript source, configuration, declarations, tests, quality diagnostics, and package artifacts. Node.js and Bun runtime, module, loading, and emitted-JavaScript mechanics appear on these pages only where they explain how TypeScript source executes, emits, resolves, declares, or reaches a consumer. Standalone JavaScript source guidance, JavaScript or mixed-language eligibility, JavaScript checking through `allowJs` and `checkJs`, and JSDoc typing of `.js` files are out of scope, and a JavaScript-only request is reported as out of scope.

Read only the portions relevant to the current project outcome. None of these pages defines a preferred stack, exhaustive support matrix, implementation procedure, or universal project policy.

## Route By Question

- **Which runtime ran, and what processed the TypeScript.** Clue: a `.ts` entry point, a green type check beside a failing run, or a specifier that resolves for the checker but not for the loader. [Runtime And Project Structure](runtime-and-project-structure.md) keeps the source-to-consumer chain, the processing differences among native stripping, transpiling, and a build step, module kind and resolution, project scope, and the canonical mixed-clue case.
- **Which workspace and invocation the evidence concerns.** Clue: a manifest, lockfile, workspace glob, installed binary, or script line is being read as proof of what executed. [Manager, Workspace, And Invocation Evidence](manager-workspaces-and-invocation.md) separates the evidence layers, the manager-specific routes, and the competing-lockfile question.
- **What a quality command actually covered or changed.** Clue: a check passed, missed a file, or rewrote output, and the question is which program members, target set, mode, or written files it touched. [Quality Scope And Tool Effects](quality-scope-and-tool-effects.md) separates program membership, target selection, check versus write mode, and tool roles that are not interchangeable.
- **Why a test or a measurement misleads.** Clue: a test did not run although a command exited zero, or a coverage percentage moved without a behavior change. [Test Execution And Measurement](test-execution-and-measurement.md) keeps collection per runner, isolation, assertion strength, and the coverage denominator separate, with provider disagreements visible.
- **What a framework build emitted, and who consumes it.** Clue: a build or dev command succeeded, and the question is which mode, adapter, output, declared target, and host or package received the result. [Framework Output And Consumers](framework-output-and-consumers.md) keeps the invocation-to-consumer chain, the entity categories, and the Vite boundary distinct.
- **Which source supplied a configuration value.** Clue: a setting is missing, defaulted, inherited, or differs between a shell and a runtime, and no precedence order is evident. [Configuration Loading And Validation](configuration-loading-and-validation.md) separates the five configuration sources, precedence per loader and surface, parsing from validation, and exposure controls.
- **Which surface produced a diagnostic or telemetry output.** Clue: a line appeared twice, carried a sensitive value, or arrived from a console, channel, report, context manager, or exporter. [Diagnostics And Telemetry](diagnostics-and-telemetry.md) separates the six diagnostic surfaces and keeps documented maturity and naming disagreements visible.
- **Whether work runs in parallel, stopped, or still completes.** Clue: concurrency was assumed from `await`, a cancellation was requested, a stream write stalled, or shutdown returned before the work did. [Concurrency And Lifecycle](concurrency-and-lifecycle.md) separates event-loop ordering, a cancellation request from an effect already produced, and cancelling a wait from destroying the work.
- **What a public source or API contract requires.** Clue: an import of a packed subpath fails, or a declaration, public name, or runtime module format must stay compatible for a consumer. [Source And API Conventions](source-and-api-conventions.md) keeps the shared cross-layer rule and the public-compatibility boundary, maps each failure to its layer, and routes outward: everyday source choices — import form, names, comment placement, file boundaries, and public-surface preferences — belong to the style workspace's method hub, `node-source-style-guide -> reference/source-style-guidance.md`, and the ordered packed-subpath diagnosis and artifact validation belong to the package workspace's canonical consumer page, `node-package-distribution -> reference/consumer-resolution-and-declarations.md`, which this page does not restate.

Every route is a reading pointer only. A route grants no operation, tool, edit, permission, sequence, approval, or completion authority.

## Applicability

Each claim holds only for its named runtime, tool, version, mode, and evidence type. A documentation claim describes what that source says; it does not show that a specific project uses the feature or that the feature works in an untested combination. Rolling documentation can change, and runtime or package-manager behavior may differ across versions. Versioned examples illustrate the stated documentation or metadata rather than a tested compatibility matrix, supported baseline, universal default, or recommendation.

## Boundaries

This map is an index only. The reference supports outcome owners with shared vocabulary and bounded mechanics. It does not own production changes, test-only work, dependency or environment mutations, quality workflows, package artifact creation, or planning. It grants no tool, write, approval, publication, or completion authority.
