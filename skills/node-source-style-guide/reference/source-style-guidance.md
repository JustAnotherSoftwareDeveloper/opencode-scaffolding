# Contextual Source-Style Guidance

TypeScript source style in a Node.js or Bun project is a set of project conventions, not a universal standard. When conventions are unclear or conflict, separate mechanical output, configured diagnostics, established source patterns, and the behavior promised to callers. These are different kinds of evidence; no single ordering resolves every conflict. Repository and API contracts govern the outcome, while style examples inform choices only where those contracts leave room. This reference stays inside TypeScript source: Node.js and Bun mechanics appear only where they explain how that source executes, emits, resolves, or reaches a consumer, and a JavaScript-only request is out of scope.

Every statement below is one of two kinds. A hazard statement describes an observable consequence — a value, a call site, a type check, or a failure mode behaves in a particular way — and it is bound to the version, mode, and configuration it names. A convention statement describes a preference whose rationale is reader comprehension, consistency, tooling, or churn avoidance, and it binds only the publisher or codebase that states it. Which kind a sentence is decides how far it can constrain a change. Documentation comments sit exactly on that line: a JSDoc or TSDoc type expression records an intent for readers and tools, and it does not validate runtime input, so checking the value itself is a separate mechanism owned by [Types, Validation, And Generics](types-validation-and-generics.md#validate-the-value-not-just-the-type).

## Establish The Relevant Context

Before applying an example, identify the target package and source boundary, the code's intended consumers, and the repository's applicable formatting and lint configuration. Read the configuration and scripts first, inspect nearby maintained files for conventions the tools do not encode, then check the module's callers and public consumers for API constraints. Compare nearby maintained code that serves a similar role rather than copying an arbitrary file. Check whether the change is internal or affects an exported module, package subpath, declaration, or documented runtime behavior.

Use configuration to explain what tools currently format or report, not as proof that every existing file follows it. Use neighboring code to infer local practice, not as authorization to reproduce a defect or violate a caller contract. When those sources conflict, name the conflict and the affected surface; do not invent a universal priority rule and do not silently settle on a house rule.

External guides are scoped evidence. Google's [TypeScript/JavaScript style guide](https://google.github.io/styleguide/tsguide.html) says it derives from Google's internal guide, is adjusted for public use, and may not apply outside its context. The [TypeScript contributor coding guidelines](https://github.com/microsoft/TypeScript/wiki/Coding-guidelines) describe conventions for contributors to that project. Either guide can supply useful candidate conventions, but neither is automatically binding in another repository, and both are rolling pages whose current text governs.

## Keep Formatting, Linting, And Conventions Distinct

[Prettier](https://prettier.io/docs/en/) describes parsing and reprinting supported source to provide consistent formatting. Its output can settle configured whitespace and wrapping choices; it does not decide whether an exported name, type boundary, or comment is appropriate.

[typescript-eslint](https://typescript-eslint.io/getting-started/) distinguishes correctness-oriented recommended rules from stylistic rules whose purpose is consistency. The [consistent-type-definitions rule](https://typescript-eslint.io/rules/consistent-type-definitions/) illustrates that a project may choose consistent use of `interface` or `type`, while exceptions can matter. The existence of a rule page does not establish that a target project enables that rule, and an enabled rule is evidence of configured lint behavior rather than of a runtime contract.

For a disagreement, first determine which tool actually governs the changed files and whether it is in formatting, diagnostic, or mutating mode. Then consider the established convention and the source/API requirement. A green linter result describes only what that invocation checked — its rule set, option settings, and selected files — not the program as a whole or the API contract its callers depend on, and a formatter's rewrite is not a design review.

The difference is easiest to see in two changes that both look like style edits. Reformatting a file is a layout rewrite: the formatter reprints the same declarations in the configured layout, and no type or runtime behavior changes. Converting a compatible object `type` alias to an `interface` with the same members is a change to the exported type: an interface can be merged by a consumer's own declaration, so the conversion adds a merge point the alias never provided, and a merge with conflicting members is rejected rather than ignored. A discriminated union is not one of those cases; it has no equivalent interface form, so that conversion is not available there at all ([TypeScript Handbook: Object Types](https://www.typescriptlang.org/docs/handbook/2/objects.html)).

## Make Source Decisions With Evidence

- **Imports and exports:** Follow the module format and resolver this package actually uses, not a neighboring file that belongs to another package scope. Prefer the import form that keeps dependency and symbol origin clear under the local convention; the named-versus-namespace preference in Google's guide is one attributed consideration, not a default. A barrel export can simplify imports and also widen the exposed surface, so verify that consumers are meant to depend on it. Do not transplant an external guide's named-export or default-export prohibition without checking the local patterns, tooling, and the package's existing consumer contract. The import-form examples are in [Imports, Names, And Comments](imports-names-and-comments.md#choose-an-import-form-for-the-surface).
- **Names and type patterns:** Search adjacent declarations and call sites for the established naming and type patterns. `interface` and `type` can both express many object shapes, but a merge point, a union, a mapped-type requirement, or a configured consistency rule can decide the choice; a configuration that enables the typescript-eslint rule records a consistency setting, not a semantic winner. The local-versus-exported naming examples are in [Imports, Names, And Comments](imports-names-and-comments.md#keep-local-names-and-exported-names-separate), and what the compiler can prove at a call site belongs to [Types, Validation, And Generics](types-validation-and-generics.md).
- **Comments and documentation:** Keep comments that explain non-obvious rationale, constraints, or invariants. For a public declaration, document what a caller needs — rejected input, thrown errors, documented defaults, cancellation — rather than restating the implementation. Confirm each claim against runtime behavior rather than the comment's assertion of it. The comment forms are in [Imports, Names, And Comments](imports-names-and-comments.md#write-comments-for-what-the-code-cannot-say).
- **File and module boundaries:** Place code where package scope, ownership, and dependency direction stay clear. Splitting a small helper can improve reuse and can also create an accidental public import path; check whether the file is reachable through a package entry point or only imported internally.
- **Public surface:** Treat exported names, subpaths, declaration files, and the runtime module format as one consumer-facing design surface. Narrowing visibility reduces accidental coupling; removing an export or subpath that someone already uses can still break that consumer. Establish the supported consumer contract before calling a change harmless.

For a concrete style disagreement, record what the formatter rewrites, which lint rule reports the issue and at what scope, what neighboring maintained code does, and whether the disputed construct is public. Resolve only the decision those facts support. When the repository is inconsistent or the intended API is unknown, describe the competing evidence and leave the choice to the owner who decides; this reference neither enforces nor rewrites style. One worked case applies that order to formatter output, effective lint configuration, neighboring modules, a publisher preference, type semantics, and the package contract: [Walk One Alias-Versus-Interface Conflict](imports-names-and-comments.md#walk-one-alias-versus-interface-conflict).

The pages that answer the everyday questions keep their own examples: [Imports, Names, And Comments](imports-names-and-comments.md), [Functions, Callbacks, Receivers, And State](functions-callbacks-receivers-and-state.md), [Values, Defaults, Objects, And Iteration](values-defaults-objects-and-iteration.md), [Async And Error Boundaries](async-and-error-boundaries.md), and [Types, Validation, And Generics](types-validation-and-generics.md).

## File And Module Organization

Organize modules around the repository's established boundaries and the dependencies they own. Avoid creating a general utility module just to avoid a small local helper, but do not duplicate behavior whose shared contract is already explicit. File names and extensions can participate in module resolution and runtime interpretation, so use the project's established module form and verify imports against its actual build/runtime path.

Exports decide which of those boundaries are visible. An export expresses an intended module boundary rather than a convenience for a file that happens to reach the symbol: an internal helper does not become public because one more module imports it, and a subpath or named export that a consumer already uses stays part of the surface even when it looks incidental. In a Node package, the package `exports` map, its conditions, and the module format affect how consumers resolve entry points, and the [Node.js packages documentation](https://nodejs.org/api/packages.html) describes those runtime surfaces; any compatibility claim about them depends on the package's supported Node versions and its actual consumers. Module resolution and runtime mechanics beyond that belong to `node-project-reference -> reference/runtime-and-project-structure.md`, and declaration consumption with package entry points belongs to `node-package-distribution -> reference/consumer-resolution-and-declarations.md`.

When a codebase has mixed conventions, inspect the nearest comparable module and the consuming call sites. A migration may intentionally follow a new pattern, but that is a project-level change rather than evidence that the old pattern was universally wrong. Keep unrelated reorganization out of a narrowly scoped change.

## Public API And Runtime Contracts

Review a proposed source-style change as API-sensitive when it changes an exported name, package subpath, declaration, parameter or return shape, error behavior, or documented timing/side effects. Consider the consumer-visible surface separately from internal readability.

- Preserve documented imports and supported package paths unless the task explicitly changes that contract.
- Keep declarations aligned with runtime behavior. An optional callback in a declaration should reflect whether the runtime can omit it; overload ordering can affect caller resolution.
- Follow the individual API's error propagation contract. A function may throw synchronously, reject a promise, invoke an error callback, or emit an `error` event. Do not generalize one mechanism to other APIs.
- Node documents `error.code` as more stable across minor versions than `message` for Node core errors. Do not extend that claim to third-party errors without their contract.
- Do not call a change compatible merely because its TypeScript types compile. Identify the actual runtime, package entry point, and consumer contract relevant to the request.

These are review considerations, not a semantic-versioning policy or a determination that every change is breaking. Concrete compatibility requires the package's supported versions and actual consumers. The channels themselves, and how a caller observes each one, are on [Async And Error Boundaries](async-and-error-boundaries.md#read-the-error-channel-from-the-api-contract).

## Common Misreadings And Limits

- **A formatter chose the style.** It chose configured layout, not names, comments, module design, or API shape.
- **A lint rule is enabled because documentation exists.** Inspect the target configuration and effective files; documentation describes an available rule, not project adoption.
- **The repository consistently does this, so it is safe.** A repeated pattern is evidence of local practice, not proof that it meets current requirements or can be changed without consumer impact.
- **A guide is authoritative because it is detailed.** Its own audience and scope still apply.
- **A declaration-only edit cannot affect users.** Typed consumers can observe declaration shape even when JavaScript output is unchanged.
- **A source-style request authorizes broad cleanup.** Style context does not expand the requested change or grant implementation authority.

The cited guides and project documentation provide examples of their stated practices, not a survey of all teams or a tested Node/Bun compatibility matrix. No repository, package, compiler, or runtime was tested here. Use the target project's supported versions, configuration, and consumer contract for concrete decisions. Nothing here selects or presupposes Vite or forms an implicit pipeline, and no compatibility claim substitutes for the target package's supported versions and its actual consumers.
