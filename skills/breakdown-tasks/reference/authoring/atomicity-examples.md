# Atomicity Examples

Use these contrasts alongside **Atomicity and alignment** in the loaded
`task-contract` documentation skill.

Before assigning skills, the boundary-review record for each applicable packet must
capture the request-result inventory, the fixed-predecessor split decision for every
candidate, and a closed disposition for every review warning. After publishing
candidates, the delegator must compare that closed record and the final task set with
the original request before accepting the packet for display or dispatch. Structural
validity never supplies this acceptance.

## Split

- **Assess authentication design and dependency risk:** two findings can be accepted
  or retried separately. Create two tasks; synthesize only when requested.
- **Analyze migration risk, then propose a bridge:** the assessment is a predecessor
  result consumed by the proposal. Create two dependent tasks.
- **Research session evidence, then create an audit skill:** separate the research
  inventory, audit-contract decision, skill creation, and validation.
- **Revise the API reference and deprecation policy:** the documentation and policy
  changes have separate acceptance decisions.
- **Research packet construction and write a proposal:** separate source discovery,
  behavioral analysis, recommendation, proposal authoring, and proposal validation.
- **Implement a change and run tests:** separate implementation and verification
  when the tests can execute against a fixed implementation result.
- **A warning identifies analysis plus implementation in one candidate:** record
  `split`, create the analysis handoff and dependent implementation task, and close
  the
  warning only after both tasks appear in the inventory and final set.

## Narrow Keep-Together Exceptions

- **Read an already-identified parser reference while implementing one specified
  option:** the read itself produces no discovery, finding, or decision.
- **Change a source schema and regenerate its client:**
  keep the state change together only when separation would leave an invalid
  repository state. Record `accepted-indivisible` with the one shared repository
  state, one verification boundary, and concrete invalid-state harm; put
  independently executable verification in another task.

## Wrong Reasons To Keep Together

Do not merge results because they share a file, report, topic, release, skill,
dependency, or final deliverable. Do not merge because the intermediate handoff
is small or was not explicitly requested. If uncertain, split. Do not accept a packet
because its structure validates or warnings are absent. For every applicable packet,
reject optional adoption, backwards compatibility, migration, legacy, transition,
prior-format, absent-record acceptance, and alternate paths.
